# 开源框架与前沿方案 — 取材标准

适用于技术选型、开源框架对比、agent 与 AI 工程的方案调研。

---

## 来源优先级

**1. 项目仓库本身（最高）**

README 里的自述哲学和「为什么不是 X」段落，比任何第三方评测都准确——它是维护者对竞品的公开表态，通常直接写明了对方的短板和自己的取舍。

其余重点：last commit 时间、issue 里的抱怨、release notes 的修改（改动本身就是踩坑的证据）。

**2. 头部公司的官方产出**

Anthropic、OpenAI、Cursor、GitHub 等的工程博客、官方文档、开源规范仓库（如规范正文 + 配套评测集）、模型或产品的发布说明。

看的是他们**自己怎么做**，不是他们怎么宣传产品。

**3. 一手访谈与内部实践披露**

维护者、负责人的长访谈，价值高于任何二手总结。这类内容会给出具体数字（每天多少次发布、一个功能试了多少版原型）和放弃某做法的原因。

**4. 论文与第三方机构实测**

arXiv、会议论文、高校或独立机构的对照实验。**优先找带对照组和量化结果的**，尤其是结论与主流叙事相反的——这类最能防止跟风。

**5. 技术媒体与测评文章（最低）**

大量是 SEO 内容。只用来发现「还有哪些项目值得查」，不作事实依据。看到就去查原仓库或原论文。

---

## GitHub 项目的判断

| 看什么 | 怎么用 |
|---|---|
| star 绝对值 | 判断是否进入视野，不作为质量依据 |
| star 短期增速 | 判断是否是当前活跃方向 |
| last commit / last release | 三个月无提交的谨慎采用 |
| open issue 的内容 | 找真实使用中的问题，比 star 有用 |
| 是否有清晰的 license 和治理归属 | 捐给基金会的通常更稳定 |
| README 的竞品对比段 | 最快拿到该赛道的方案分类 |

**star 数各来源经常打架。** 以仓库页面的实时数字为准，并注明查询日期。写不到确切数字时给区间并说明来源不一致，不要挑一个好看的。

---

## 记录时注意

**区分「项目主张」和「已验证」。** README 说自己解决了什么，是主张；issue 和第三方实测里的表现，才是验证。两者分开记。

**注明版本和日期。** 这个领域三个月就换代，半年前的对比结论通常已失效。

**只记产品与方案层面的做法，不记它的内部技术实现。** 用什么语言、怎么做缓存，与需求无关。

**结论与主流相反的证据要单独标出来。** 例如某项实测显示自动生成上下文文件会降低任务成功率，这类反向证据在决策时权重高于十篇跟风介绍。

**至少覆盖三个项目或三种方案。** 只查一个就下结论无效。
