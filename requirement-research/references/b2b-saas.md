# B 端 SaaS 功能调研 — 取材标准

适用于计费、额度、权限、组织架构、审批、用量统计这类企业侧功能的调研。

这类调研的特点是：**没有 GitHub star 可以参考，也几乎没有技术博客写这些**。有效信息藏在产品自己的文档里，需要换一套取材方法。

---

## 来源优先级

**1. 官方帮助中心 / 文档中心（最高）**

这是唯一会把边界条件写清楚的地方。查具体功能的说明页，重点看那些「注意」「说明」「例外情况」的小字——那些通常就是他们踩过坑之后补上去的。

**2. 定价页 / 套餐对比页**

能反推出他们的额度模型、计费单位、超额策略。定价页上的脚注尤其有价值，往往写着「超出部分按 X 计费」「未使用额度不结转」这类关键口径。

**3. 更新日志 / release notes**

最能看出「踩了什么坑」。搜功能名 + changelog，看这个功能上线后改过什么。改动本身就是问题的证据：某个字段后来加了确认弹窗，说明当初有人误操作过。

**4. 用户社区 / 论坛的抱怨帖**

官方社区、Reddit、产品的 feature request 板块。抱怨帖直接告诉你哪些设计在真实场景下不成立。搜「功能名 + 具体痛点词」比搜功能名本身有效。

**5. 第三方测评 / 对比文章（最低）**

大量是 SEO 内容，可信度低，只用来发现「还有哪些家值得查」，不用作事实依据。看到就去查这些家的官方文档，不要直接引用测评的结论。

---

## 选哪几家去查

**别只看行业老大。** 老大的方案往往为超大规模设计，在中小场景下是过度设计。至少覆盖三档：

- 一家规模最大的（看它的完整形态）
- 一家中等的、增长快的（看它怎么做减法）
- 一家和本产品定位最接近的（看它的实际约束）

**优先查有公开文档的。** 文档写得细的公司，通常也是这个功能想得清楚的公司。

**国内外都要看。** 计费、税务、对公支付这类，国内外差异极大，只看一边会得出错误结论。

---

## 这类功能常见的坑（检索时重点找）

调研时主动去找这几类信息，它们是 B 端功能最容易出问题的地方：

| 方向 | 要找的具体问题 |
|---|---|
| 额度 / 计费 | 未用完的额度是否结转、怎么算超额、退款怎么冲账、周期切换时怎么处理 |
| 权限 | 权限变更是否即时生效、降权后已有数据怎么办、谁能授予谁 |
| 组织架构 | 人员调岗时归属怎么变、部门删除时下属数据怎么办、同步冲突怎么解 |
| 审批 | 审批中的单据被修改怎么办、审批人离职怎么办、能不能撤回 |
| 用量统计 | 统计口径的时区、数据延迟多久、跟计费数据对不上怎么解释 |

这些问题在产品介绍页上永远看不到，只在帮助中心的小字和社区抱怨里。

## 记录时注意

**引用要写清楚是哪个版本、哪一年的信息。** B 端产品改版频繁，两年前的做法可能已经推翻。

**区分「他们的产品设计」和「他们的技术实现」。** 只记前者。他们用什么数据库、怎么做异步，和需求无关。

**注意套餐差异。** 同一个产品在不同套餐下策略可能完全不同（免费版限制更严、企业版更宽松）。记的时候要标明是哪个档位。
