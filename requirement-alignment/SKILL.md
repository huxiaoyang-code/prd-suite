# 需求对齐

把需求拆成**一条条能被单独确认或推翻的陈述句**，不写成有背景铺陈、目标价值的 PRD。

工作区、开场路由、编号规则、归档，见 `AGENTS.md`。

---

## 形态问题还是口径问题

**拿不准就当形态问题。**

| 形态问题 → 先出探索稿 | 口径问题 → 直接文字对齐 |
|---|---|
| 新页面、新模块，无可参照的现有页面 | 在现有页面上加字段、改规则、调口径 |
| 涉及信息架构选择（几个 tab、侧边栏、列表还是卡片） | 改的是计算逻辑、状态流转、权限 |
| 页面上大部分内容是「看什么」而非「算什么」 | 页面形态本身没争议 |
| 对外网站、落地页、C 端界面 | |

探索稿放 `explore/`，文件名写清这版在试什么（`v3-顶部tab.html`，不是 `v3.html`）。**保真度不设限**，与定稿 mockup 的低保真要求相反。

胜出的形态进 C 区。**被否决的版本不留文件，只在 D 区留一行理由**，如「试过顶部 tab，否决因为二级筛选放不下」。

## 对齐动作

**1. 先抽象。** 两三句话说清整体链路（「A 上传凭证 → 解锁 B → 用户配置 C → 下发给 D」），确认后再列条目。用户话里有歧义的抽象（「三种方案」其实是「两个可选项的组合」）要指出并请确认，不默认接受表面说法。

**2. 已说清的列成编号列表。** 按模块分组，每条只讲一件事，具体到可被验证——「密码最少 8 位」，不是「密码有长度要求」。

**3. 没说清的逐条提问。** 每条说明它决定了哪个字段结构、哪条计算公式或哪个下游边界。存在多种解读时列出差异和后果，不替用户做主。优先暴露影响数据结构和核心计算的点，其余标注「可以边做边补」。需要外部佐证才能定的，建议先调研，不假设行业惯例。

**4. 用户确认后在原编号体系上更新或追加**，不重写导言、背景、目标。确认引出矛盾（改了一个口径导致另一条自相矛盾）时主动指出，给 2~3 个处理方式，不悄悄替用户拍板。

**5. 用户说「确认需求」「最终版」时输出完整清单。** 按模块分组，组内边界在前、下游字段在后；只含已确认条目；自己补的默认规则单独标注；不加总结段落和后续展望，列表结束就结束。

---

## 格式

- 全程逐条编号列表，不用大段散文
- 小标题用一级模块名（「一、范围与边界」）
- 每条尽量一句话说完；对比多个选项时才用表格
- 术语可中英混用，不堆砌黑话
- **不写代码、不写技术实现方案、不画架构图**，除非用户明确要求进入方案设计。探索稿的 HTML 不算

---

## 反例

- 开篇写「本次需求旨在解决 XX 场景下的 XX 痛点」
- 一条里塞多个信息点：「字段配置项包括名称、类型、默认值、校验规则等，同时还需要考虑历史数据兼容」
- 用户只确认 3 个点，却把整个清单连没确认的部分一起重述
- 自己补的默认规则不标注
- 用户推翻一条时直接删掉不留理由
- 形态类需求上来就写文字描述
- 没确定目录就开始记录
- 一轮结束不更新头部三行
- 初始化完成后停下来等用户重新提问

## 补丁区

模型变强后应整段删除。

**每轮结束都要更新头部三行和相应条目。** 现在需要反复强调，是因为模型容易在长对话里忘记维护外部文件。这是这套机制唯一的接续依据，漏了下次进来就接不上。

**编号前缀固定 C/O/R/D。** 为了保证编号不被混用。
