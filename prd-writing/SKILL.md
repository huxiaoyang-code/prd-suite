# PRD 撰写

一次产出三样：`PRD.md`（规则、口径、边界）、`mockup.html`（可点可切状态的形态）、`shots/`（mockup 快照，PRD 引用它）。

三者靠**同一套区域编号**对齐：mockup 标 ①②③，PRD 按 ①②③ 分节，验证表挂在对应节，快照文件名带页面序号。不引入额外 ID 系统。

`shots/` 是生成物，可全删重跑，人不手工往里放东西。上线后用真实截图覆盖同名文件，引用路径不变。

工作区与文件格式见 `AGENTS.md`。

---

## 准入

| 情况 | 动作 |
|---|---|
| alignment.md 不存在 | 先把理解的需求逐条列出请用户确认，不凭对话硬写 |
| O 区有影响页面结构或计算口径的未决点 | 列出各自会导致哪一块写不下去，请用户先定 |
| O 区其余未决点 | 带着走，进「待确认」章节 |
| 有条目跟本需求的页面对不上 | 提出来问，可能是从别的需求飘过来的 |
| `explore/` 存在 | mockup 由 C 区确认的那一版降保真改造，不重新画 |

## 承重规则

只有承重规则配验证表。四类：**数字计算**（金额怎么算、折扣怎么算）、**状态流转**（经过哪些态、什么条件触发）、**边界处理**（超上限、为 0、并发提交）、**权限可见性**（谁能看、谁能点）。

文案措辞、默认排序、提示语位置不算承重。有界面的功能通常 15~25 条。

**四类不均匀分布。** 无界面需求集中在边界处理和状态流转，另两类可能为零，总数明显偏少，不要凑数。

## 骨架

```
# PRD | 功能名

# 一、背景与目标
## 1.1 背景          现状缺什么
## 1.2 产品目标      ✅ 开头，3~5 条；末尾写本期不做什么

# 二、产品形态
## 前提              必须满足 / 最好满足
## 入口设计          挂在哪个模块、哪些页面、本期做哪些
## 跳转关系          页面与弹窗跳转图

# 三、页面结构设计
## 3.1 页面一
![总览-正常态](shots/01-总览-正常.png)
### ① 区域名        区域说明 → 该区规则 → 承重规则的验证表

# 四、公共规则        只留跨区域的
# 五、状态流转        有单据流转的必写
# 六、全局边界        网络异常、并发、跨页一致性
# 七、待确认          表格：问题 / 建议 / 谁定
# 八、交付清单        文案、配置项；不含图片
```

**规则下沉**：规则写在所属区域下面，第四章只留跨区域的。

**无界面需求**：三章换成「结构设计」，页面换成文件或模块，其余机制不变。不产出 mockup 和 shots，在 PRD 里说明，**不画假页面凑数**。

**网站、落地页**：三章占全文 70%，第四、五章可能整节为空，**直接删掉不写「无」**，重点转到界面文案。

## 页面章节

快照图片（多状态放多张，每张下一行说明是哪个态）→ 按 ①②③ 逐区块说明。

每个区块：**区域说明**（这块干什么、有哪些字段，连贯叙述，口径写在字段旁边不单开一节）→ **规则**（承重规则编号 `R3-1`，仅被别处引用时才需要编号）→ **验证表**。

| 条件 | 预期表现 | 判定 |
|---|---|---|
| 输入值 > 允许的最大值 | 输入框下方红字提示超出上限，确认按钮置灰 | 提示文案出现且按钮不可点 |
| 可选项为 0 | 输入框置灰，提示「暂无可选项」 | 输入框不可编辑 |

**条件 = 什么情况，预期表现 = 界面怎么反应，判定 = 怎么算做对了。** 第三列是可被机械核对的那一句，写不出来就回去改第二列，不要写「符合预期」。

每条规则 2~4 行，覆盖正常态、边界态、异常态。

## mockup.html

单文件，不依赖外部资源，双击能开。

- **视觉低保真**：单一灰阶（白、#f5f5f5、#e0e0e0、#999、#333），无品牌色、无阴影、无圆角装饰、无图标库
- **结构高保真**：区块划分、字段名称、按钮文案、表格列名都是真实要做的
- **顶部一排状态切换按钮**，点击整页切换（空态 / 正常 / 异常 / 待审批 / 失败）
- 多个页面和弹窗放同一文件，顶部导航切换；每个区块左上角标 ①②③
- 假数据的数量级和格式要真实：金额带千分位、时间用真实格式、列表至少 3 行且长短不一
- **界面文案按需求内容写**：按钮写清点了会发生什么（「确认删除」而非「提交」），同一动作全流程用同一个词，空态和错误态给出下一步方向
- 底部固定写：`本页仅表达需求形态，视觉与交互细节以设计稿为准。`

## 写作规则

- **需求描述用连贯叙述**：现状缺什么 → 要做到什么 → 边界在哪。对照类内容才用表格
- **改动关系加粗标注** **新增** / **改造**
- **计算公式用代码块**，必要时补恒等式（`剩余库存 = 总库存 − 已锁定 − 已发出`）
- **引用块只用于容易做反的地方**，每份最多 3~5 处

> 上调不需要确认、下调需要，是因为上调不损害任何人，下调会直接影响已在进行的流程。

---

## 不要写的内容

属于研发自行定义的范围：表结构、字段清单、字段类型、接口清单与路径、请求响应格式、状态码英文枚举、技术选型、架构方案、定时任务的实现方式（写「每月 1 日清零」不写调度实现）、幂等并发锁（写「一张单只发放一次」不写幂等键设计）、非承重规则的验收清单。

「待确认」章只放需要业务、财务、产品拍板的问题，来自 O 区里不卡结构的那些，每条注明谁定并给倾向性建议。技术实现问题不进 PRD。

---

## 收尾

1. 说明需要截哪几张图、每张切到什么状态、文件名（`序号-页面名-状态.png`）。截图由用户完成，PRD 里先按约定路径写好引用。
2. 列出**在 alignment.md 里找不到对应 C 编号的规则**，请用户确认。不要默默混进去。
3. 提醒用户跑一次 prd-review。

## 补丁区

模型变强后应整段删除。

**快照需人工截图。** 自动截图涉及无头浏览器和中文字体渲染，稳定性不足。

**验证表固定三列。** 为了保证第三列不被省略。

**区块编号手工标注。** ①②③ 靠人肉在两边保持一致，等有工具校验时删。

**准入写成表。** 因为模型倾向于一接到需求就开始写。
